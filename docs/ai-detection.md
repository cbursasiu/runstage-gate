# AI-generated change detection

RunStage Gate can flag pull requests that look AI-generated and apply stricter policy to them.
It's off unless you enable it in `.runstage/gate.yml`. Like the rest of the config, it is read
from the PR's **base** commit, so a PR can't turn detection or policy off for itself.

```yaml
ai_detection:
  enabled: true
  commit_trailers: true                                    # default
  branch_prefixes: [cursor/, codex/, copilot/, claude/, devin/, ai/]   # default
  labels: [ai-generated, ai-assisted, generated-by-ai]     # default, case-insensitive
  markers: ["written with our assistant"]                  # extra phrases (default none)
  policy:
    require_checks: [tests, ai-review]   # must name checks in `checks`
    require_approval: false
```

## Signals

It uses heuristics only and is provider-agnostic. Any one signal marks the change as AI-generated.

| Signal | Source |
| --- | --- |
| `Co-authored-by:` trailer naming a known AI tool (Claude/Anthropic, Copilot, Cursor, Codex/OpenAI, ChatGPT, Gemini, Devin, Aider, Codeium/Windsurf, CodeWhisperer, Tabnine, Jules) | commit messages in `merge-base..head` (runner, via git) |
| Generator markers such as `Generated with Claude Code`, `🤖 Generated with`, `Generated by Copilot`, plus your `markers` | commit messages, PR title and body |
| Head branch starts with one of `branch_prefixes` | PR head branch |
| PR has one of `labels` | PR labels |
| PR author is a known AI bot account (`…[bot]`) | PR author |

Branch, labels, title and body come from the code host's webhook. The GitHub App stores them on
the job, merging them in when `pull_request` arrives after `check_suite`. A job a runner has
already claimed is not updated. Local `runstage-gate run` only sees commit messages.

Detection can be wrong in both directions: humans can use these branch names, and AI tools
can leave no trace. Use it to add scrutiny, not as proof.

## What it changes

- Every check gets `RUNSTAGE_AI_GENERATED` (`1` or `0`; `0` when detection is off) and
  `RUNSTAGE_AI_SIGNALS` (one reason per line).
- The check summary shows `AI-generated: yes (reasons)` or `no signals found`. The result
  carries `ai: { generated, signals }`, and history stores and shows it.
- `policy.require_checks`: for AI-generated changes these checks become required, and if one
  is skipped (e.g. agent checks are off on the runner) it becomes an **error**, so the gate fails
  instead of passing without it.
- `policy.require_approval`: AI-generated changes get a failing required `ai-approval` policy
  result. Someone with write access can then approve the gate
  ([approvals.md](approvals.md)); a new push needs approving again.
